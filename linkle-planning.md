# Linkle — Build System Planning

## Workspace Model

Every Hylian project is a **workspace**. A workspace is a directory containing a `linkle.work` file and one or more members.

```
myproject/
├── linkle.work
├── linkle.lock        ← generated, do not edit
├── myApp/
│   ├── linkle.pkg
│   └── src/
│       └── main.hy
└── myLib/
    ├── linkle.pkg
    └── src/
        ├── lib.hy
        └── extern.hyi ← only for C FFI boundaries
```

### Member Types

**Binary** — a program that can be compiled and run. Has an entry point.

**Library** — adds functionality to binaries. No entry point. Not runnable on its own.

---

## File Roles

| File | Role |
|---|---|
| `linkle.work` | Workspace root — declares members and their paths |
| `linkle.pkg` | Per-member manifest — name, version, type, dependencies |
| `linkle.lock` | Generated lock file — exact resolved versions and hashes |
| `.hy` | Hylian source — compiled directly, no intermediate step |
| `.c` | C source — compiled together with `.hy` files transparently |
| `.hyi` | C FFI interface — only needed when wrapping external C libs |

`.hy` and `.c` files are compiled together as a unit. The compiler reads `.hy` source directly for type info (like Zig), so `.hyi` files are **only** for defining the interface of external pre-built C libraries, not for Hylian-to-Hylian imports.

## File Formats

### `linkle.work`

```
project myproject

myApp {
    path: ./myApp
    type: Bin
}

myLib {
    path: ./myLib
    type: Lib
}
```

The `type` field here is the authority. `linkle.pkg` type is ignored for workspace members.

### `linkle.pkg`

```toml
name = "myApp"
version = "1.2.0"
type = "Bin"
hylian = "0.2.0"

[deps]
nayru  = "^2.0.0"   # from hylian.lol registry
myLib  = "*"        # resolved locally via linkle.work — version ignored
```

For local workspace members, use `"*"` as the version. Linkle checks `linkle.work` first before hitting the registry, so `myLib` resolves to the local path automatically.

### `linkle.lock`

Generated automatically. Commit this to version control.

```toml
# generated by linkle — do not edit
version = 1

[[package]]
name = "nayru"
version = "2.3.1"
source = "registry+https://hylian.lol/packages"
hash = "sha256:a1b2c3d4e5f6..."
deps = ["farore@1.0.0"]

[[package]]
name = "farore"
version = "1.0.0"
source = "registry+https://hylian.lol/packages"
hash = "sha256:9f8e7d6c5b4a..."
deps = []

[[package]]
name = "myLib"
source = "local"
path = "./myLib"
# no hash — always rebuilt from source when changed

[[package]]
name = "myApp"
source = "local"
path = "./myApp"
deps = ["nayru@2.3.1", "myLib"]
```

Registry packages get an exact resolved version + content hash. `^2.0.0` in `linkle.pkg` resolves to e.g. `2.3.1` at lock time — everyone on the team builds `2.3.1`. Transitive deps (deps of deps) also get entries.

## Package Registry

Single registry at `hylian.lol/packages`. No searching GitHub, no fetching arbitrary URLs.

Rules:
- Packages are **immutable once published** — a version cannot be overwritten, only yanked
- Yanked packages still resolve if already in a lock file (won't break existing projects)
- Upload with `linkle publish`

---

## Dependency Resolution

Uses **Minimum Version Selection (MVS)**, stolen from Go:

- If `myApp` requires `nayru ^2.0.0` and `myLib` requires `nayru ^2.1.0`, pick `2.1.0`
- No SAT solver, no backtracking, fully deterministic
- No "latest wins" surprises on `linkle update`

Version syntax:

| Syntax | Meaning |
|---|---|
| `"1.2.3"` | Exact pin |
| `"^1.2.3"` | Compatible with 1.x.x, >= 1.2.3 |
| `"~1.2.3"` | Patch updates only, >= 1.2.3 < 1.3.0 |
| `"*"` | Local workspace member — no version constraint |

To avoid dependency hell:
- Sole registry = no version drift between sources
- Immutable publishes = no surprise breakage
- Lock file = reproducible builds everywhere
- MVS = deterministic resolution, no conflicts

## C FFI

### Seamless external C libs

External C libraries are declared in `linkle.pkg` and used transparently in source:

```toml
# linkle.pkg
[c_deps]
raylib = { link = "raylib", header = "raylib.h" }
```

```hylian
// main.hy
import raylib

raylib.DrawCircle(100, 100, 50.0, raylib.Color { r: 255, g: 255, b: 255, a: 255 })
```

The compiler parses the C header at compile time and generates an internal `.hyi` representation. C types are mapped to Hylian native types transparently — no `c_int`, no `callconv`, no unsafe blocks visible to the user.

### C type mapping

| C type | Hylian type |
|---|---|
| `int` / `c_int` | `i32` |
| `unsigned int` | `u32` |
| `const char*` | `str` |
| `void*` | `*any` |
| `float` | `f32` |
| `double` | `f64` |
| `bool` | `bool` |

For edge cases where a C function mutates a pointer (can't safely map to `str`), annotate with `@unsafe`:

```
extern fn ReadIntoBuffer(buf: @unsafe *u8, len: i32): void
```

### Manual `.hyi` (fallback / pre-built libs)

For pre-built libs without headers, or until `@cImport` is implemented, write `.hyi` by hand:

```
// raylib.hyi
@link("raylib")

extern struct Color { r: u8, g: u8, b: u8, a: u8 }
extern struct Vector2 { x: f32, y: f32 }

extern fn DrawCircle(centerX: i32, centerY: i32, radius: f32, color: Color): void
extern fn DrawText(text: str, x: i32, y: i32, fontSize: i32, color: Color): void
extern fn Fade(color: Color, alpha: f32): Color
```

The compiler always works through `.hyi` internally — `@cImport` just auto-generates it so users don't have to write it manually.

## Linkle CLI (planned)

```
linkle init              — scaffold new workspace or member
linkle build             — build all members
linkle build myApp       — build specific member
linkle run myApp         — build and run a binary
linkle add nayru@^2.0.0  — add registry dep to current member
linkle update            — re-resolve deps within constraints, update lock
linkle publish           — publish current library to hylian.lol
linkle fetch             — download all deps from lock file
```
